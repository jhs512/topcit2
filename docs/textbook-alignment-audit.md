### 노트 02/8

- 보강: 서술·예측 분석 — 패턴과 원인을 구분한다 — 서술적 분석은 주어진 자료의 패턴을 설명하고 예측적 분석은 학습한 모형으로 새 입력의 결과를 예상합니다. 예를 들어 고객의 기존 구매 이력으로 다음 구매를 예측할 수 있지만, 그 이력이 구매를 일으킨 원인이라는 뜻은 아닙니다. 광고 효과처럼 원인에 관한 결정을 내리려면 비교 집단과 다른 영향 요인을 추가로 확인해야 합니다. 이 마지막 구분은 교재의 분석 분류에 보완한 실무 해석 원칙입니다.

### 추가로 학습할 목표

- **스택과 큐**: 스택은 마지막에 넣은 원소를 먼저 꺼내는 LIFO, 큐는 먼저 넣은 원소를 먼저 꺼내는 FIFO 구조입니다. 재귀 호출 관리와 대기 작업 처리처럼 꺼내는 순서가 다른 문제에 알맞은 구조를 선택합니다. 확인 질문: A, B, C 순서로 넣었다면 스택과 큐에서 꺼내는 순서는 각각 무엇인가요? [소프트웨어 개발 PDF 39쪽](https://jhs512.github.io/topcit/viewer/index.html?book=01&page=39)
- **이진 탐색과 깊이 우선 탐색**: 이진 탐색은 정렬된 자료의 중간값과 비교해 탐색 범위를 절반씩 줄입니다. 깊이 우선 탐색은 한 경로를 먼저 깊이 따라간 뒤 되돌아오며, 스택이나 재귀 호출로 구현할 수 있습니다. 확인 질문: 정렬하지 않은 목록에 이진 탐색을 바로 적용할 수 없는 이유는 무엇인가요? [소프트웨어 개발 PDF 49쪽](https://jhs512.github.io/topcit/viewer/index.html?book=01&page=49)
- **UML과 디자인 패턴**: UML은 구조와 동작을 여러 관점의 다이어그램으로 표현하는 모델링 언어입니다. 디자인 패턴은 반복되는 설계 문제에 활용할 수 있는 해결 구조를 정리한 것으로, 완성된 코드 자체와는 다릅니다. 확인 질문: 클래스 간 관계와 객체 간 시간순 메시지를 각각 어떤 다이어그램으로 나타낼까요? [소프트웨어 개발 PDF 73쪽](https://jhs512.github.io/topcit/viewer/index.html?book=01&page=73)
- **컴파일러와 인터프리터**: 컴파일러는 소스 코드를 다른 표현의 코드로 번역하고, 인터프리터는 프로그램을 해석하며 실행합니다. 실제 언어 실행 환경은 두 방식을 함께 사용할 수 있으므로 언어 이름만으로 실행 구조를 단정하지 않습니다. 확인 질문: 소스 코드, 번역 결과, 실행 단계를 나누어 두 방식의 차이를 설명해 보세요. [소프트웨어 개발 PDF 90쪽](https://jhs512.github.io/topcit/viewer/index.html?book=01&page=90)

### 추가로 학습할 목표

- **함수 종속과 정규화**: 정규화는 함수 종속을 살펴 관계를 분해하여 삽입·갱신·삭제 이상을 줄이는 과정입니다. 제2정규형은 제1정규형에서 부분 함수 종속을 제거하고, 제3정규형은 제2정규형에서 이행 함수 종속을 제거합니다. 확인 질문: 주문번호와 상품번호가 복합키일 때 상품명은 키 전체에 종속하나요, 일부에 종속하나요? [데이터 이해와 활용 PDF 72쪽](https://jhs512.github.io/topcit/viewer/index.html?book=02&page=72)
- **SQL의 조회 조건과 그룹 조건**: SELECT로 필요한 열을 선택하고 WHERE로 행을 제한합니다. GROUP BY는 집계할 그룹을 만들고 HAVING은 집계된 그룹에 조건을 적용합니다. 확인 질문: 개별 주문 금액이 1만 원 이상인 행을 고르는 조건과 고객별 주문 합계가 10만 원 이상인 그룹을 고르는 조건은 어디에 둘까요? [데이터 이해와 활용 PDF 107쪽](https://jhs512.github.io/topcit/viewer/index.html?book=02&page=107)
- **동시성 제어와 직렬 가능성**: 여러 트랜잭션을 함께 실행하더라도 결과의 일관성을 유지해야 합니다. 직렬 가능성은 동시 실행의 결과가 어떤 직렬 실행의 결과와 같도록 하는 성질이며, 잠금 등은 이를 위한 제어 수단입니다. 확인 질문: 두 거래가 같은 잔액을 읽고 각각 덮어쓸 때 어떤 갱신이 사라질 수 있나요? [데이터 이해와 활용 PDF 122쪽](https://jhs512.github.io/topcit/viewer/index.html?book=02&page=122)
- **ETL과 OLAP**: ETL은 여러 원천의 데이터를 추출·변환·적재하는 과정입니다. OLAP은 분석용 데이터를 차원별로 집계하거나 세부 수준으로 내려가며 살펴보는 방식입니다. 확인 질문: 월별·지역별 매출 합계에서 특정 지역의 일별 매출로 내려가는 분석은 무엇을 바꾸나요? [데이터 이해와 활용 PDF 138쪽](https://jhs512.github.io/topcit/viewer/index.html?book=02&page=138)
- **지도·비지도·강화 학습**: 지도 학습은 정답이 붙은 예제로 입력과 출력의 관계를 학습합니다. 비지도 학습은 정답 없이 데이터의 구조를 찾고, 강화 학습은 행동의 보상을 바탕으로 정책을 학습합니다. 확인 질문: 정답이 있는 불량품 분류와 구매 패턴에 따른 고객 군집화는 각각 어떤 학습에 해당하나요? [데이터 이해와 활용 PDF 153쪽](https://jhs512.github.io/topcit/viewer/index.html?book=02&page=153)

### 추가로 학습할 목표

- **WBS와 작업 패키지**: WBS는 프로젝트 범위를 산출물과 관리 가능한 작업 단위로 계층적으로 나누는 구조입니다. 작업 패키지가 분명해야 일정·비용을 추정하고 완료 여부를 확인하기 쉬워집니다. 확인 질문: ‘서비스 개발’만 적은 작업과 ‘주문 조회 API 및 인수 조건’까지 나눈 작업은 관리상 어떻게 다른가요? [프로젝트관리 및 테크니컬커뮤니케이션 PDF 86쪽](https://jhs512.github.io/topcit/viewer/index.html?book=06&page=86)
- **3점 추정**: 3점 추정은 낙관치 O, 최빈치 M, 비관치 P를 이용해 불확실성을 반영합니다. 교재의 PERT 가중 평균은 (O + 4M + P) / 6이며, 단일 확정 납기를 보장하는 식은 아닙니다. 확인 질문: O=4일, M=6일, P=10일이면 기대 기간은 약 며칠인가요? [프로젝트관리 및 테크니컬커뮤니케이션 PDF 94쪽](https://jhs512.github.io/topcit/viewer/index.html?book=06&page=94)
- **주공정법과 여유 시간**: 주공정법(CPM)은 작업 기간과 선후 관계를 바탕으로 전체 일정을 결정하는 경로를 찾습니다. 자원 제약 등을 별도로 고려하지 않은 네트워크에서 가장 긴 경로가 최소 완료 기간을 결정하며, 주공정 작업의 지연은 전체 완료에 영향을 줍니다. 확인 질문: 두 병렬 경로가 12일과 16일이면 완료 기간을 결정하는 경로는 어느 쪽인가요? [프로젝트관리 및 테크니컬커뮤니케이션 PDF 98쪽](https://jhs512.github.io/topcit/viewer/index.html?book=06&page=98)
- **획득가치 분석**: PV는 계획 작업의 예산 가치, EV는 완료 작업의 예산 가치, AC는 실제 비용입니다. SPI=EV/PV와 CPI=EV/AC를 사용해 일정과 비용 성과를 따로 살핍니다. SV=EV−PV도 금액으로 표현한 일정 성과 차이이며 지연 일수는 아닙니다. 확인 질문: PV=100만 원, EV=80만 원, AC=90만 원일 때 SPI와 CPI는 각각 1보다 큰가요, 작은가요? [프로젝트관리 및 테크니컬커뮤니케이션 PDF 110쪽](https://jhs512.github.io/topcit/viewer/index.html?book=06&page=110)
- **품질보증과 품질통제**: 품질보증은 품질을 확보하도록 절차와 활동이 적절하게 수행되는지 살피고, 품질통제는 산출물의 결과를 측정·검사하는 데 초점을 둡니다. 검사만 늘리는 것과 결함을 예방하는 프로세스 개선을 구별합니다. 확인 질문: 코드 검토 절차를 점검하는 활동과 인수 테스트 결과를 확인하는 활동은 초점이 어떻게 다른가요? [프로젝트관리 및 테크니컬커뮤니케이션 PDF 116쪽](https://jhs512.github.io/topcit/viewer/index.html?book=06&page=116)

- **테크니컬 라이팅의 검토**: 기술 문서는 정확성뿐 아니라 독자가 필요한 내용을 찾고 실행할 수 있는지를 검토해야 합니다. 구조·용어·표현을 점검하고 실제 작업 순서와 설명이 일치하는지 확인합니다. 확인 질문: 설치 설명서의 문장이 문법적으로 맞아도 처음 사용하는 사람이 실패한다면 무엇을 추가로 검토해야 할까요? [프로젝트관리 및 테크니컬커뮤니케이션 PDF 49쪽](https://jhs512.github.io/topcit/viewer/index.html?book=06&page=49)
