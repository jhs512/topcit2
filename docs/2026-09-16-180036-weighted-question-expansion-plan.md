# 공식 평가영역 비율에 맞춘 문제은행 확충 계획

## 요청

모든 과목의 문제를 늘리되 단순 총량보다 실제 시험의 영역별 비율을 우선한다. 기존 600문항과 학습기록을 보존하고, 문항 작성·검토·화면 검증·커밋·푸시·배포 확인까지 진행한다.

## 확인한 사실과 적용 기준

- 확인일: 2026-09-16.
- [TOPCIT 공식 변경 공지](https://www.topcit.or.kr/board/notice/detail.do?seq=842)는 이번 웹 도구에서 직접 본문을 확보하지 못했다. [고려대학교가 게시한 2026년 공식 시험안내 PDF](https://swuniv.korea.ac.kr/bbs/swuniv/979/177637/download.do)의 1쪽 표를 확인했다. 공지와 안내문을 혼동하지 않는다.
- 전체 시험 배점은 소프트웨어 36.5%, 데이터 26.5%, 시스템아키텍처 및 정보보안 23.5%, IT비즈니스(윤리·PM·TC 포함) 13.5%다.
- 객관식은 네 영역 각각 15문항으로 문항 비율은 각 25%다. 전체 문항 수는 영역별 21·19·18·17개이므로 배점 비율과도 다르다.
- 이 사이트는 객관식 연습문제은행이다. 전체 시험 배점 비율로 배분한다면 ‘시험 중요도를 반영한 연습량 배분’이라고 표시하고 실제 객관식 문항 구성과 같다고 표시하지 않는다.
- 사용자에게 배점 비율과 객관식 비율 중 선호를 질문했다. 답변 전에는 전체 배점 비율을 기준으로 계획한다. 다른 기준을 선택하면 데이터 작성 전에 목표표를 변경한다.
- 8개 사이트 과목별 세부 출제비율은 확인한 공식 자료에 없다. 공식 4개 영역의 합계를 지키고, 내부 배분은 학습 범위와 기존 문항을 고려한 자체 편집 기준으로 명시한다.

## 배점 비율 기준 목표안

기존 비즈니스 300문항을 삭제하지 않으려면 총량이 최소 약 2,223개여야 한다. 네 영역의 배점 비율을 정수로 정확히 맞출 수 있는 총량은 200의 배수다. 윤리·소통에도 서로 다른 상황의 문제를 보강하기 위해 총 3,000문항을 목표로 한다. 정해진 수를 채우기 위한 문장·숫자만 바꾼 복제는 허용하지 않는다.

## 작업 단계

1. 공식 영역·사이트 과목·출제기준 코드의 대응과 목표 개수를 데이터로 관리한다. 비율 기준은 한 곳에서 읽고 자동 검사한다.
2. 소프트웨어·데이터의 공식 학습목표를 문제은행의 기준 목록에 추가한다. 교재 원본 `books.mjs`의 source에서 목차·학습목표·관련 본문을 먼저 확인한다. 구판에 없는 최신 내용은 현재 1차 자료로 확인한다.
3. 전체 학습목표에 대해 개념 구분, 코드·SQL·계산 결과, 상황 적용, 오류 원인과 수정 판단 등의 출제 항목을 작성한다. 목적이 다른 문제인지 검토한 뒤 문항으로 확장한다.
4. 새 문항은 JSON에 저장하고 고유 ID와 revision 1을 부여한다. 기존 600문항은 그대로 유지한다. 핵심 개념·정답인 이유·실제 오답과의 구분을 설명하고 계산 문제에는 식과 대입 과정을 쓴다.
5. 과목 분류와 문제 로더가 네 공식 영역을 처리하도록 확장한다. 기존 URL, 보기 섞기, id@revision 진도, 초기화 범위, 05·06 호환 주소를 유지한다.
6. 문제은행 화면에 공식 영역별 목표·현재 개수·배분 기준을 표시한다. 준비 중 안내와 README·학습방법의 수치를 실제 완료 상태에 맞춰 고친다.
7. 목표 개수·정확한 비율·전체 기준 범위·ID 중복·질문 중복·보기 유일성·정답·해설·출처·기존 기록 호환을 검사한다. 코드·SQL·계산 결과는 실행으로 대조한다. 형식 검사를 내용 검토로 대신하지 않는다.
8. PC·모바일에서 8과목과 3모드, 진도·히스토리·필터·음성 읽기를 확인한다. 문항 증가에 따른 전체모드 반응 속도도 확인한다.
9. 완료된 데이터를 커밋·푸시하고 Pages 배포와 공개 문제 개수를 확인한다. 목표에 못 미친 상태를 완료로 보고하지 않는다.

## 주요 영향 파일

- `shared/learning-subjects.mjs`: 기존 분류 유지 및 신규 두 영역 분류.

- `README.md`, `study/index.html`의 실제 제공 범위 안내.

## 구현 결과와 검증 기록

- 네 영역 1,095·795·705·405문항, 총 3,000문항. 전체 배점 비율과 정확히 일치한다. 여덟 과목은 목표표의 수량을 모두 채웠다.
- 기존 600문항은 원본 JSON 객체의 SHA-256으로 내용·보기·정답·ID·revision 보존을 검사했다. 기존 저장 키와 URL을 유지했다.
- 신규 2,400문항의 실제 구성: 개념 판단 106개, 비즈니스·윤리·관리·소통 상황 105개, Python 연산 순서 1,052개, SQL 조건·집계 732개, 페이지 교체 120개, CPU 스케줄링 80개, 접근통제 정책 205개.
- 소프트웨어·데이터의 106개 출제기준을 추가해 공식 세부 기준 163개 각각에 최소 한 문항이 대응한다. 이 검사는 주제별 학습량이 고르게 분포한다는 뜻이 아니다.
- 반복 연습은 고정 입력에서 연산·조건·실행 순서·규칙의 관계를 바꾼다. Python 문항은 각 단계를 생략하면 결과가 달라져야 하며, 접근 정책은 실제 검사 경로가 같은 중복을 제외했다. 회사명이나 숫자만 바꾸는 방식은 사용하지 않았다.
- **실행 연습의 비중이 높다.** 서로 다른 개념 3,000개를 작성한 것이 아니며, 영역 내부의 세부 주제 비중까지 실전을 재현하지 않는다. 이 한계를 README·학습방법·문제 목록에 표시했다.
- 2,189개의 실행 연습 정답을 Python·SQLite 실행과 별도 시뮬레이션으로 대조했다. 형식 검사와 정답 실행 검증을 서술형 문항의 전문 검수와 혼동하지 않는다.
- PC·모바일 1440·720·390·320px에서 과목 목록·학습 경로·수량·진도·히스토리·초기화·기존 링크 통과. 1440·390px에서 새 문항 풀이와 세 모드 확인.
- 전체모드에서 1,000개 이상 문제의 TTS 버튼을 추가할 때 레이아웃 읽기·쓰기가 반복되는 지연을 발견했다. 표시 여부를 먼저 일괄 확인한 뒤 버튼을 추가하도록 수정했고 TTS 켜기·끄기·재활성화, 텍스트 범위, 교재·사례·문제, 문장 강조·문맥, PC·모바일 회귀 검사를 모두 통과했다.
- 개념 문항 106개는 분류 제목이 답을 알려주지 않도록 개념에 맞는 상황을 고르는 형태로 작성했다. 상위·하위 개념이 동시에 정답이 될 수 있는 보기를 검토하고 조정했다.
- 로컬 검증 완료. main 커밋·푸시 및 공개 배포 확인 단계.
