# 교재를 제외한 학생용 콘텐츠 전면 개편 계획

작성: 2026-09-17 15:30 KST

## 1. 목표와 독자

독자는 IT 지식이 조금 있는 고등학생으로 설정한다. 앱·웹사이트·파일·로그인은 알지만, 기업의 업무 절차나 서버 운영·데이터베이스·경영 용어를 배웠다고 가정하지 않는다. 실제 수업 대상이나 시험 응시 대상을 고등학생으로 바꾼다는 뜻은 아니다.

읽은 학생이 다음 세 가지를 자신의 말로 설명할 수 있어야 한다.

1. 이 용어가 가리키는 대상이나 행동은 무엇인가?
2. 어떤 상황에서 왜 필요한가?
3. 조건이 달라지면 선택이나 결과가 어떻게 달라지는가?

문장만 짧게 고치지 않는다. 설명에 빠진 배경·원인·과정을 채우고, 한 문단에 섞인 개념을 나눈다. 전문 개념과 문제 풀이 수준은 유지하되, 학생이 표현을 해독하느라 막히지 않게 한다.

## 4. 문장을 새로 쓰는 기준

### 설명의 순서

기본 흐름은 **뜻 → 즉시 이해할 예 → 이유와 과정 → 조건과 한계**다. 문단마다 이 제목을 반복하지 않고 자연스러운 글로 연결한다. 개념상 상황부터 시작하는 편이 좋으면 상황을 먼저 제시한다.

- 첫 설명에서 대상과 행동을 밝힌다. `의존성을 관리한다`는 `결제 처리가 다른 서버의 응답을 기다린다면, 그 서버가 멈췄을 때 결제도 멈추는지 확인한다`처럼 쓴다.
- 전문용어를 버리지 않고 필요한 시점에 푼다. `가용성`은 `필요할 때 서비스를 사용할 수 있는 정도`처럼 설명한 뒤 사용한다.
- 영문 약어는 처음 쓰는 곳에서 뜻과 쓰임을 설명한다. 영문 풀네임만 추가하는 것으로 끝내지 않는다.
- `따라서`, `그러므로` 뒤에 나오는 결론을 앞 문장이 실제로 뒷받침하는지 확인한다.
- `높은 수준`, `최적화`, `안정성`, `효율`, `관리`만 쓰지 않고 무엇의 속도·시간·비용·정확성을 말하는지 밝힌다.
- 학교·동아리·예약·쇼핑몰처럼 익숙한 상황을 사용한다. 회사 업무가 핵심이면 그 업무가 무엇인지 먼저 설명한다. 모든 개념을 억지로 학교 비유로 바꾸지 않는다.
- 하나의 설명 안에서는 같은 사례를 이어 간다. 예시를 늘려 새 용어가 더 많아지지 않게 한다.
- 문단은 한 가지 생각을 다룬다. 짧은 문장을 무조건 늘어놓거나 정해진 글자 수를 채우지 않는다.
- `항상`, `모두`, `반드시`는 적용 조건을 확인한다. 쉬운 설명을 위해 틀린 일반화를 만들지 않는다.
- 표·그림은 비교나 흐름을 이해하는 데 필요한 곳에만 넣고 무엇을 보여 주는지 제목을 붙인다.

### 핵심노트

각 노트는 독립 링크로 읽어도 이해되어야 한다. 앞 노트를 읽었다고 가정해 필수 용어 설명을 생략하지 않는다. 본문과 예시가 같은 말을 반복하지 않게 하고, 확인 질문은 방금 배운 개념으로 답할 수 있게 한다. 확인 질문의 답과 근거는 검토 기록에도 남긴다.

### 사례

기존 필수 구획 `이 글에서 배우는 교훈 → 들어가기 전에(선택) → 본문 → 결론`을 유지한다. 일반 원리와 구체적인 적용을 나누되, `추상적인 문장`이라는 원본 필드명이 어려운 문장을 쓰라는 뜻은 아니다.

본문에는 **누가 어떤 일을 하다가 → 어떤 문제가 생겼고 → 왜 그 방법을 골랐으며 → 무엇을 했고 → 어떤 결과가 생겼는지**가 드러나야 한다. 결론은 결과에서 확인할 수 있는 교훈까지만 말한다. 예상 피해를 실제 피해로, 부분 개선을 완전한 성공으로 바꾸지 않는다. 실제 사례 4편은 사건의 1차 출처를 다시 확인한다. 가상 이야기에는 교육용 설정임을 표시한다.

### 문제은행

문제의 읽기 난도와 평가 난도를 구분한다. 지문은 조건·주체·순서를 명확하게 하고, 정답을 알아내야 하는 개념은 설명에 슬쩍 노출하지 않는다. 보기들은 같은 질문에 답하도록 맞춘다.

해설은 `핵심 개념: → 정답인 이유: → 오답 구분:`을 유지한다. 정답 보기의 표현을 반복하지 말고 지문의 어떤 조건 때문에 정답인지 설명한다. 오답은 실제 보기별로 다른 이유를 적는다. 계산은 단위·식·대입·결과 해석을, 코드·SQL은 결과에 영향을 주는 실행 단계를 보여 준다.

공통 생성 설명을 고쳐도 개별 지문·보기·계산 결과가 적절한지는 별도 검토한다. 생성기 한 곳을 고쳤다는 이유로 해당 유형의 모든 문항을 검토 완료로 표시하지 않는다.

## 5. 기준 원고: 시스템아키텍처 첫 노트

교재 03의 목차, I장의 학습목표, PDF 24–25쪽 본문을 읽고 정의의 범위를 확인했다. 다음 글은 원문 인용이 아닌 자체 설명의 개편 기준안이다. 쇼핑몰과 비용 판단은 개념을 적용하기 위한 가상 예시다.

**시스템아키텍처 — 어떤 일을 해야 하는지부터 확인한다**

시스템아키텍처는 서비스를 제공하는 프로그램·데이터·서버 등을 어떻게 구성하고, 서로 연결해 동작하게 할지 정하는 것입니다. 쇼핑몰이라면 고객이 누른 주문 버튼이 주문 처리 프로그램으로 연결되고, 주문 내역이 데이터베이스에 저장되도록 전체 구조를 설계하는 일입니다.

교재에서는 이를 넓은 의미와 좁은 의미로 나눕니다. 넓게 보면 프로그램을 어떻게 나눌지 정하는 응용 아키텍처, 데이터를 어떤 구조로 저장하고 서로 연결할지 정하는 데이터 아키텍처, 서버·네트워크와 실행에 필요한 소프트웨어를 어떻게 배치할지 정하는 기술 아키텍처를 함께 다룹니다. 좁게 말할 때는 이 가운데 기술 아키텍처를 뜻합니다.

설계자는 장비를 고르기 전에 이 시스템이 어떤 일을 해야 하는지 확인해야 합니다. 해야 할 일에 따라 필요한 처리 속도와 장애에 대비할 방법이 달라지기 때문입니다.

예를 들어 쇼핑몰의 주문·결제가 멈추면 고객이 구매를 완료하지 못합니다. 반면 관리자용 월간 통계는 잠시 늦게 조회되더라도 당장 구매를 막지는 않습니다. 담당자는 각 기능이 멈췄을 때 누가 어떤 일을 못 하게 되는지 확인하고, 얼마나 빨리 처리하고 복구해야 하는지 정합니다.

빠른 처리와 복구를 준비하려면 더 많은 요청을 처리할 장비, 고장에 대비한 추가 서버, 복구 훈련 등이 필요할 수 있습니다. 모든 기능에 똑같이 높은 목표를 적용하면 장비 비용과 관리 작업이 늘어납니다. 그래서 중요한 업무에 필요한 수준부터 정하고 그 수준을 충족할 방법을 고릅니다.

**확인 질문:** 주문·결제와 월간 통계 중 하나만 먼저 장애 대비를 강화할 수 있다면 무엇을 고르겠습니까? 멈췄을 때 고객이 못 하게 되는 일을 근거로 설명해 보세요.

**검토용 답의 방향:** 이 예시에서는 주문·결제부터 검토한다. 구매를 완료하지 못하는 직접적인 영향이 있기 때문이다. 다만 실제 우선순위는 각 업무의 이용 시점과 중단 영향을 확인해 결정한다.

## 6. 실행 순서와 산출물

### 단계 1 — 빠짐없는 검토 목록과 기준선

- 실제 원본에서 160개 노트·160편 사례·3,000문항의 ID와 과목을 수집한다.
- 35개 추가 학습, 과목 도입, 수업·안내 화면의 원본도 별도 목록으로 관리한다.
- 검토 상태는 `미검토 → 원문 확인 → 재집필 → 내용 검증 → 생성 확인 → 화면 확인 → 배포 확인`으로 기록한다. 수정할 필요가 없는 항목도 유지 이유를 기록해야 내용 검증을 완료할 수 있다.
- 각 항목에 어려운 표현, 누락된 배경, 교재 근거, 수정 원본, 확인 질문의 답, 남은 문제를 남긴다.
- 현재 문항의 ID·revision·정답·보기 순서·출처와 교재 파일의 해시를 기준선으로 보관한다.

### 단계 2 — 대표 원고로 방식 확정

- 위 시스템아키텍처 원고와 함께 데이터·보안·비즈니스 등 8과목에서 노트 1개와 사례 1편씩 작성한다.
- 개념 문제, 상황 판단, 계산, 코드, SQL, 규칙 해석의 해설을 각각 작성한다.
- 정의를 풀면서 뜻을 바꾸지 않았는지, 예시만 기억하고 개념을 놓치지 않는지 확인한다.
- 노트 설명의 문자열 자동 접합과 사례 교훈의 첫 문장 자동 추출을 명시적인 완성 원고로 바꾸는 방식을 정한다. 제목·설명·예시·질문·교훈의 실제 편집 위치를 하나로 명확히 한다.
- 여러 문단을 렌더링할 수 있게 하되 기존 앵커·목차·TTS 표시를 유지한다. 완성 화면에서 읽어 본 뒤 나머지 항목에 적용한다.

### 단계 3 — 8과목의 노트·사례·교재 연결 해설 전면 개편

과목별로 관련 교재의 목차·학습목표·해당 본문을 먼저 읽고, 노트 20개와 사례 20편을 함께 고친다. 초안 작성 순서는 현재 지적된 시스템아키텍처 → 정보보안 → IT 비즈니스 → 윤리 → 프로젝트 관리 → 테크니컬 커뮤니케이션 → 소프트웨어 → 데이터로 한다. 공개 화면의 기존 과목 순서는 유지한다.

과목 하나의 설명만 바꾸고 완료로 넘기지 않는다. 과목 도입, 노트, 예시, 질문, 사례 교훈·본문·결론, 교재 연결 요약, 추가 학습 안내를 하나의 묶음으로 마무리한다. 실제 사례는 사실관계를 재검증한 뒤 표현을 수정한다.

### 단계 4 — 문제은행 전체

- 과목별로 지문·보기·해설을 읽고, 계산·실행 유형은 풀이 유형별로도 교차 검토한다.
- 원본 600문항과 생성 2,400문항의 편집 경로를 구분한다. 생성 입력과 생성기를 고친 후 JSON을 다시 만들고 수정 유실 여부를 확인한다.
- 의미가 같은 해설 보완은 revision을 유지할 수 있다. 질문·보기·정답 의미 또는 보기 순서가 바뀌면 revision을 올리고 변경 사유를 남긴다.
- 기존 600문항의 해시를 고정하는 검사가 있으므로 의도한 수정 목록을 먼저 대조하고 기준선을 갱신한다. 검사를 삭제하거나 통과를 위해 무조건 새 해시로 덮지 않는다.
- 문항 수·배분의 변경은 이번 글쓰기 개편에서 하지 않는다. 별도 균형 재편 결과를 적용하게 되면 두 계획의 변경 목록을 합친다.

### 단계 5 — 수업·안내와 전체 문맥

홈·목록·학습방법·수업 자료·시험 안내·출제기준의 자체 설명·강사소개·문제 조작 안내까지 같은 독자 수준으로 검토한다. 안내는 짧고 직접적으로 쓰고 불필요한 사례를 덧붙이지 않는다. 시험 일정·규정·법령·최신 보안 권고를 다루는 문장을 수정할 때는 해당 시점의 공식 출처를 확인한다.

직접 공유하는 수업 페이지의 기존 이용 흐름을 유지한다. 기존 기획과 최종 원고의 ID 대응도 갱신한다. `topcit`와 `topcit2`에 같은 원고가 있더라도 자동으로 양쪽을 덮어쓰지 않고 게시 원본과 동기화 대상부터 확인한다.

### 단계 6 — 검증·게시

1. 변경된 원본으로 `build:practical`, `build:cases`, 필요한 `build:syllabus`, `lec/build.mjs`, 문제 생성기를 실행한다. 영향 없는 생성기는 불필요하게 실행하지 않는다.
2. `npm test`, `test:core`, `test:case-schema`, `tests/textbook-alignment.test.mjs`, 문제 실행 검증 등 해당 검사를 수행한다.
3. 노트 160개·사례 160편·문항 3,000개·추가 학습 35개의 누락, 중복 ID, 빈 필드, 깨진 참조와 미검토 항목을 확인한다.
4. 교재 원문과 전사본의 내용 해시를 전후 비교해 변경이 없는지 확인한다.
5. PC 1440px, 모바일 390px·320px에서 긴 문단, 표, 보기, 코드의 가독성을 확인한다. 각 과목의 목록→본문, 목차, 키보드, 다크모드, TTS, 문제의 전체·설명·랜덤 모드와 학습기록을 검증한다.
6. 기존 링크 정책과 검사기의 차이를 먼저 확인한다. 사용자가 지정한 자체 PDF 뷰어 링크는 페이지를 검증해 사용하고, 기존 게시 주소·호환 링크가 끊어지지 않게 한다. 교재 본문은 수정하지 않는다.
7. 다른 작업의 변경을 제외하고 완성한 변경을 커밋·푸시한다. Pages 성공과 공개 페이지·데이터의 실제 반영을 확인한 뒤 배포 완료로 기록한다.

## 7. 합격 기준

자동 검사 통과와 쉬운 설명은 별개다. 사람이 읽는 내용 검증에서 다음을 확인한다.

- IT를 조금 아는 학생이 추가 검색 없이 해당 문단의 상황을 이해할 수 있다.
- 핵심 전문용어의 뜻, 등장인물의 역할, 선택의 이유가 설명되어 있다.
- 주장의 직후에 이해를 돕는 설명이나 예가 있으며, 예가 주장을 실제로 뒷받침한다.
- 학생이 확인 질문에 답할 근거가 본문에 있다. 문제은행 지문에는 정답을 노출하는 불필요한 힌트가 없다.
- 내용이 교재와 맞고, 자체 적용·가상 설정·현재 사실이 구분된다.
- 실제 사례의 인과관계와 성과를 과장하지 않는다.
- 수정 필요 항목을 빠짐없이 고쳤으며 유지 항목에도 검토 근거가 있다.
- 재생성해도 옛 문구가 돌아오지 않고, 최종 화면에서 문단이 자연스럽게 이어진다.

글자 수·문장 길이·특정 금칙어만으로 쉬운 글이라고 판정하지 않는다. 자동 검사는 누락·구조·호환성을 확인하고, 이해 가능성은 내용별로 판단한다. 학생 독자의 실제 읽기 피드백을 얻지 못했다면 학생 검증 완료라고 쓰지 않는다.

확대 실행한 기존 보조 검사에서 남은 실패도 기록한다. `speech-highlight.mjs`는 원문 `API`와 발음 변환된 `에이피아이`의 문자열 포함 비교에서 실패했다. `theme-browser.mjs`는 현재 화면에 없는 이전 교재 버튼 `#theme`를 기다리다 실패했다. `site-navigation.mjs`는 마지막 고정 좌표 바깥 클릭 후 닫힘 기대에서 실패했다. 해당 구현과 검사 파일은 이번 개편에서 변경하지 않았으며 전체 보조 검사 통과로 보고하지 않는다. 개편용 브라우저 검사는 현재 공통 버튼과 실제 새 원고를 대상으로 통과했다.
