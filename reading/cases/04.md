# 정보보안 이해와 활용 · 핵심노트 기반 가상 사례

## SEC-01 · 급여 파일의 세 가지 사고는 같은 문제가 아니었다
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 보안의 세 목표 — 기밀성·무결성·가용성을 지킨다

### 이 글에서 배우는 교훈
추상적인 문장: 기밀성·무결성·가용성은 각각 허가된 열람, 올바른 정보 유지, 필요한 때의 이용이라는 다른 목표입니다.
근거: [보안의 세 목표 — 기밀성·무결성·가용성을 지킨다 · 핵심노트 1](https://jhs512.github.io/topcit2/practical/04/#concept-1)
구체적인 문장: 회사는 급여 열람, 지급 계좌 변경, 지급일 중단을 각각의 피해로 나눠 접근·변경·복구 대책을 정했습니다.

### 본문
회사는 급여 시스템의 비밀번호를 강화했으니 안전하다고 생각했습니다. 점검에서 동료 급여를 조회할 수 있는 권한 오류, 지급 계좌를 검토 없이 바꿀 수 있는 기능, 지급일 장애 때의 복구 미준비가 각각 발견됐습니다. 비밀번호가 강해도 이 세 문제는 남아 있었습니다.

팀은 허가받지 않은 급여 열람을 막아 기밀성을, 계좌 변경 승인과 이력으로 무결성을, 지급 업무의 대체 절차와 복구 시험으로 가용성을 점검했습니다. 급여를 계산하는 사람과 계좌 변경을 승인하는 사람이 누구인지도 업무에 맞춰 정했습니다.

### 결론
같은 시스템에서도 정보가 새는 것, 값이 잘못 바뀌는 것, 필요할 때 못 쓰는 것은 피해와 대책이 다릅니다. 보안 목표를 나누면 한 제품이나 한 설정으로 모든 준비가 끝났다고 오해하기 어렵습니다.

## SEC-02 · 조회만 필요한 계정에 삭제 권한까지
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 최소 권한 — 필요한 일만 할 수 있게 한다

### 이 글에서 배우는 교훈
추상적인 문장: 자료를 조회하는 업무에 삭제 권한까지 주면 실수나 계정 도용 때 불필요한 피해가 생길 수 있습니다.
근거: [최소 권한 — 필요한 일만 할 수 있게 한다 · 핵심노트 2](https://jhs512.github.io/topcit2/practical/04/#concept-2)
구체적인 문장: 관리자는 보고서 작성 계정에 조회 권한만 주고 추가 권한은 목적과 기간을 확인해 따로 승인했습니다.

### 본문
분석 담당자는 보고서를 만들기 위해 운영 데이터베이스 계정을 받았습니다. 계정에 삭제 권한도 있어 실수로 실행한 문장이 원본에 영향을 줄 수 있었습니다.

관리자는 분석에 필요한 조회 권한만 부여했습니다. 추가 권한은 업무 목적과 기간을 확인해 별도로 승인하도록 했습니다.

### 결론
편의상 넓게 준 권한이 불필요한 피해 경로가 될 수 있었습니다. 필요한 일과 필요한 권한을 대응시키는 것이 최소 권한의 출발점입니다.

## SEC-03 · 로그인만 하면 모든 문서를 볼 수 있었다
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 인증과 인가 — 본인 확인과 허용 범위를 구분한다

### 이 글에서 배우는 교훈
추상적인 문장: 로그인은 본인 확인이며 모든 자료에 접근해도 된다는 허가는 아니므로 자료별 권한을 따로 검사해야 합니다.
근거: [인증과 인가 — 본인 확인과 허용 범위를 구분한다 · 핵심노트 3](https://jhs512.github.io/topcit2/practical/04/#concept-3)
구체적인 문장: 개발팀은 문서를 요청할 때마다 조회·다운로드 권한을 확인하고 다른 부서 계정으로도 시험했습니다.

### 본문
문서 시스템은 로그인 여부만 확인했습니다. 다른 팀 문서의 주소를 알면 권한이 없는 직원도 내용을 볼 수 있었습니다.

개발팀은 문서 요청마다 대상 문서에 대한 접근 권한을 검사했습니다. 다른 부서 계정으로 조회와 다운로드를 모두 시험했습니다.

### 결론
신원을 확인하는 것과 특정 자료를 볼 권한을 확인하는 것은 다릅니다. 로그인 성공 뒤에도 대상별 권한 검사가 필요합니다.

## SEC-04 · 검색창의 제한만 믿었던 개발자
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 시큐어 코딩 — 외부 입력과 명령을 분리한다

### 이 글에서 배우는 교훈
추상적인 문장: 화면의 입력 제한을 거치지 않는 요청도 올 수 있으므로 서버에서 값을 확인하고 데이터베이스 명령과 분리해야 합니다.
근거: [시큐어 코딩 — 외부 입력과 명령을 분리한다 · 핵심노트 4](https://jhs512.github.io/topcit2/practical/04/#concept-4)
구체적인 문장: 개발자는 서버 검증과 매개변수 질의를 사용해 입력값이 SQL 명령의 구조를 바꾸지 못하게 했습니다.

### 본문
검색 화면은 글자 수와 형식을 제한했지만 서버는 받은 검색어를 SQL 문자열에 그대로 붙였습니다. 승인된 시험에서 화면을 거치지 않은 요청을 보내자 예상과 다른 조회가 발생했습니다.

개발자는 서버에서 입력의 형식과 범위를 검사했습니다. SQL 명령과 값을 매개변수 바인딩으로 분리하고 잘못된 입력도 질의 구조를 바꾸지 않는지 시험했습니다.

### 결론
화면의 입력 제한은 서버가 받는 모든 요청을 통제하지 못했습니다. 외부 입력을 데이터로 다루고 업무 규칙과 질의 구조를 각각 보호해야 합니다.

## SEC-05 · 예제 설정에 들어간 실제 비밀 값
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 비밀과 민감정보 — 접근 키와 암호화 키의 노출을 줄인다

### 이 글에서 배우는 교훈
추상적인 문장: 이미 공유된 접근 키는 파일에서 지워도 복사본에 남을 수 있으므로 기존 키의 사용을 중지하고 새 키로 바꿔야 합니다.
근거: [비밀과 민감정보 — 접근 키와 암호화 키의 노출을 줄인다 · 핵심노트 5](https://jhs512.github.io/topcit2/practical/04/#concept-5)
구체적인 문장: 팀은 예제에 넣었던 실제 키를 교체하고 예제에는 설정 방법만 남겼습니다.

### 본문
개발자는 편의를 위해 실제 서비스의 접근 키를 예제 설정 파일에 넣었습니다. 파일이 공유되면서 누가 키를 가지고 있는지 파악하기 어려워졌습니다.

팀은 해당 키를 교체하고 실제 비밀 값은 제한된 저장 경로에서 제공했습니다. 예제에는 값의 이름과 설정 방법만 남겼습니다.

### 결론
노출된 값을 지우는 것만으로 이미 복사된 값을 회수할 수는 없습니다. 비밀 값의 저장·배포·교체를 한 흐름으로 관리해야 합니다.

## SEC-06 · 같은 취약점 공지인데 먼저 고칠 서버는 달랐다
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: CVE와 취약점 대응 — 사용 중인 구성 요소를 확인한다

### 이 글에서 배우는 교훈
추상적인 문장: 취약점 대응은 알려진 문제의 심각도와 실제 사용 버전·노출 조건·업무 영향을 함께 보고 순서를 정해야 합니다.
근거: [CVE와 취약점 대응 — 사용 중인 구성 요소를 확인한다 · 핵심노트 6](https://jhs512.github.io/topcit2/practical/04/#concept-6)
구체적인 문장: 영향 버전을 쓰는 서버를 찾고 외부 파일을 받는 서버부터 제한·수정하면서 나머지 대상의 기한도 관리했습니다.

### 본문
파일 처리 라이브러리의 취약점 공지가 나왔습니다. 회사는 제품 이름만 알 뿐 어느 서비스가 어떤 버전을 쓰는지 몰랐습니다. 확인해 보니 세 서버 중 두 대가 영향받는 버전이었고, 한 대는 외부 고객의 파일을 직접 받았습니다.

담당자는 공지의 발생 조건과 실제 설정을 비교해 외부 입력을 받는 서버의 노출을 우선 제한했습니다. 수정 버전을 시험·배포한 뒤 기능을 다시 열었습니다. 다른 영향 서버도 방치하지 않고 담당자와 수정 기한을 정했습니다. 구성 요소 목록에는 버전·사용처·책임자를 함께 남겼습니다.

### 결론
점수가 높은 공지를 읽는 것만으로 우리 회사의 대응 순서는 정해지지 않습니다. 실제 사용 버전, 노출 경로와 업무 영향을 알아야 우선순위와 임시 대책을 설명할 수 있습니다.

## SEC-07 · 웹 서버 계정으로 백업까지 지울 수 있었다
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 다층 방어 — 하나가 실패해도 피해를 제한한다

### 이 글에서 배우는 교훈
추상적인 문장: 서비스 계정 하나가 잘못돼도 백업까지 함께 손상되지 않도록 실행 권한과 백업 관리 권한을 나눠야 합니다.
근거: [다층 방어 — 하나가 실패해도 피해를 제한한다 · 핵심노트 7](https://jhs512.github.io/topcit2/practical/04/#concept-7)
구체적인 문장: 팀은 웹 서비스 계정에서 백업 관리 권한을 분리하고 보호한 백업으로 복원할 수 있는지 시험했습니다.

### 본문
운영 편의를 위해 웹 서비스 계정에 백업 저장소 관리 권한까지 부여했습니다. 웹 계정에 문제가 생기면 서비스와 복구 수단이 함께 영향을 받을 구조였습니다.

팀은 서비스 실행과 백업 관리 권한을 분리했습니다. 백업 보관 경로와 삭제 정책도 따로 관리하고 복원을 시험했습니다.

### 결론
복구 수단이 같은 실패에 함께 노출되지 않도록 해야 합니다. 여러 보호 수단은 서로 다른 피해 경로를 제한할 때 의미가 있습니다.

## SEC-08 · 경보는 울렸지만 아무도 확인하지 않았다
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: ISMS와 사고 대응 — 이상을 확인하고 대응할 담당자와 절차를 정한다

### 이 글에서 배우는 교훈
추상적인 문장: 경보를 설치하는 것에 더해 누가 확인하고 어떤 조치를 결정할지 정해야 탐지가 대응으로 이어집니다.
근거: [ISMS와 사고 대응 — 이상을 확인하고 대응할 담당자와 절차를 정한다 · 핵심노트 8](https://jhs512.github.io/topcit2/practical/04/#concept-8)
구체적인 문장: 조직은 공용 메일 경보의 담당자와 대체자를 지정하고 정상 업무 확인과 접근 제한 절차를 연습했습니다.

### 본문
대량 자료 조회 경보가 공용 메일함으로 전송되었습니다. 담당자가 정해지지 않아 실제 확인은 며칠 뒤에 이뤄졌습니다.

조직은 확인 담당자와 부재 시 대체자를 지정했습니다. 정상 업무 여부를 확인하고 필요한 접근 제한을 결정하는 절차를 연습했습니다.

### 결론
탐지는 후속 행동으로 이어져야 효과가 있습니다. 경보 수보다 누가 언제 어떤 판단을 하는지가 중요합니다.

## SEC-09 · 복구 동안 받은 주문은 어디에 있을까
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: 복구와 업무 연속성 — 사고 뒤에도 필요한 일을 한다

### 이 글에서 배우는 교훈
추상적인 문장: 시스템이 멈춘 동안 임시로 처리한 업무도 복구 뒤에 누락이나 중복 없이 반영할 방법이 필요합니다.
근거: [복구와 업무 연속성 — 사고 뒤에도 필요한 일을 한다 · 핵심노트 9](https://jhs512.github.io/topcit2/practical/04/#concept-9)
구체적인 문장: 팀은 종이 주문에 임시 번호와 접수 책임자를 정하고 복구 후 반영 여부를 대조했습니다.

### 본문
주문 시스템 장애 동안 직원들이 종이에 주문을 받았습니다. 복구 후 각자 입력하면서 같은 주문을 중복 등록하거나 일부를 빠뜨렸습니다.

팀은 임시 주문 번호와 접수 책임자를 정했습니다. 복구 뒤 반영 여부를 대조하고 중복을 확인한 후 임시 기록을 정리했습니다.

### 결론
업무 연속성은 시스템 복구 시간만의 문제가 아니었습니다. 중단 중 발생한 업무를 정상 시스템에 안전하게 연결해야 합니다.

## SEC-10 · 공유가 어려워 개인 메일을 썼다

### 이 글에서 배우는 교훈
추상적인 문장: 보안 절차대로 해서는 일을 제때 끝낼 수 없다면 우회를 줄이기 위해 공식 절차와 도구도 개선해야 합니다.
근거: [사람이 지킬 수 있는 절차 — 안전한 행동을 쉽게 만든다 · 핵심노트 10](https://jhs512.github.io/topcit2/practical/04/#concept-10)
구체적인 문장: 관리자는 개인 메일 사용을 금지하는 데서 그치지 않고 승인된 공유 방법의 처리 시간을 줄이고 잘못 보냈을 때의 신고 방법을 안내했습니다.

### 본문
회사 공유 시스템은 작은 자료 전송에도 오래 걸렸습니다. 직원들은 납기를 맞추려고 개인 메일로 업무 파일을 보냈습니다.

관리자는 금지 공지와 함께 승인된 공유 경로의 처리 절차를 개선했습니다. 외부 공유의 허용 대상과 만료, 잘못 보낸 경우의 신고 방법을 안내했습니다.

### 결론
현실에서 수행하기 어려운 절차는 우회를 부를 수 있습니다. 안전한 방법으로 일을 끝낼 수 있도록 도구와 절차를 함께 개선해야 합니다.

### 결론
임시라는 이유로 관리 대상에서 빠지면 위험이 오래 남을 수 있습니다. 임시 서버를 만들 때 담당자와 종료 날짜를 적고, 사용이 끝나면 실제로 종료했는지 확인해야 합니다.

### 결론
자료의 책임은 사용이 끝났다고 사라지지 않습니다. 장비와 매체를 외부로 보낼 때도 남아 있는 업무 자료를 확인하고 필요한 삭제·폐기를 완료해야 합니다.

## SEC-20 · 공개 전날 발견한 다른 회사의 견적서
유형: 가상 이야기 · 핵심노트 기반
핵심노트 개념: Secure SDLC — 보안 검증을 개발 전 과정에 넣는다

### 이 글에서 배우는 교훈
추상적인 문장: 보안 요구와 검증을 개발 전 과정에 배치해야 구조적인 문제를 공개 직전에 처음 발견하는 일을 줄일 수 있습니다.
근거: [Secure SDLC — 보안 검증을 개발 전 과정에 넣는다 · 핵심노트 20](https://jhs512.github.io/topcit2/practical/04/#concept-20)
구체적인 문장: 회사는 견적서 소유 회사 확인을 요구·공통 설계·거부 시험·운영 변경 검토에 연결했습니다.

### 본문
여러 회사가 쓰는 견적 서비스의 공개 전날, 보안 시험자가 파일 번호를 바꾸자 다른 회사의 견적서가 내려받아졌습니다. 로그인은 확인했지만 파일마다 어느 회사 소유인지 검사하지 않은 것입니다. 다운로드 경로가 여러 군데라 뒤늦게 모두 고치고 다시 시험해야 했습니다.

팀은 다음 개발에서 요구사항에 회사별 자료 분리를 적고 설계 단계에 공통 권한 검사 위치를 정했습니다. 구현 중 다른 회사의 파일 조회·다운로드를 거부하는 시험을 넣고, 운영에서 일괄 내려받기를 추가할 때도 같은 검사를 확인했습니다.

### 결론
공개 전 검사도 필요하지만 그때 처음 찾으면 구조 수정과 재시험이 몰립니다. Secure SDLC는 보안을 마지막 합격 검사 하나가 아니라 요구·설계·구현·시험·변경에 이어지는 작업으로 다루는 것입니다.
