소프트웨어 개발

이게 뭔가요?

사람이 하려는 일을 컴퓨터가 실제로 처리하도록 만드는 방법을 배웁니다. 필요한 기능을 파악하고, 구조를 설계하고, 코드로 구현하고, 제대로 작동하는지 확인하고 고치는 과정입니다. 식당 예약 앱이라면 고객이 시간을 고르고 예약한 뒤 취소할 수 있도록 동작을 만드는 일입니다.

왜 배우나요?

코드가 실행돼도 사용자가 필요한 일을 끝내지 못하면 문제는 남습니다. 예약 버튼을 두 번 눌렀을 때 중복 예약이 생기거나, 기능 하나를 고쳤는데 다른 기능이 멈출 수도 있습니다. 필요한 동작을 정확히 만들고, 바뀐 요구에 맞춰 안전하게 수정하는 방법을 배우기 위해 공부합니다.

코드를 작성하는 속도보다, 필요한 동작을 정확히 만들고 안전하게 바꿀 수 있는지가 중요합니다.

교재 개념의 뜻을 설명하고, 가상 업무에서 언제 왜 쓰는지 풀어 쓴 자체 해설입니다. 먼저 설명과 예시를 읽고, 확인 질문에 자신의 말로 답해 보세요. 각 항목의 관련 교재 내용에서 단원과 교재 페이지를 확인할 수 있습니다. 20개 노트는 교재 전체 요약이나 시험 중요도 순위가 아니며, 주제 끝의 추가 학습 내용도 함께 확인하세요.

1. 요구사항 추출 — 만들기 전에 불편을 확인한다

요구사항은 프로그램이 해야 할 일과 지켜야 할 조건입니다. 요구사항 공학은 필요한 내용을 찾아 분석하고 문서로 정한 뒤, 서로 같은 뜻으로 이해했는지 확인하고 변경을 관리하는 활동입니다.

사용자가 요청한 기능만 듣지 말고 그 기능으로 해결하려는 불편도 확인해야 합니다. 엑셀 내려받기 버튼을 원하는 이유가 매일 두 목록을 비교해 누락 주문을 찾기 위해서라면, 파일 제공 외에 누락을 바로 보여 주는 방법도 검토할 수 있습니다. 해결할 문제를 잘못 짚으면 기능을 빨리 만들어도 업무는 나아지지 않습니다.

가상 업무 예시

직원이 엑셀 내려받기 버튼을 요청했다고 합시다. 이유를 물어보니 주문 누락을 찾으려고 매일 두 목록을 비교하고 있었습니다. 파일 제공뿐 아니라 누락 주문을 바로 보여 주는 방법도 함께 검토할 수 있습니다.

2. 테스트 케이스와 완료 기준 — 같은 결과를 확인한다

테스트 케이스는 어떤 준비 상태에서 무엇을 입력하고 실행했을 때 어떤 결과가 나와야 하는지 적은 시험 사례입니다. 개발자와 사용자가 같은 기준으로 완료 여부를 확인하는 데 도움이 됩니다.

고객 검색이라면 찾는 이름이 있을 때만 시험하지 않습니다. 같은 이름이 두 명일 때 구분할 정보, 결과가 없을 때 안내, 권한 없는 정보가 보이지 않는 조건도 정합니다. 이렇게 기대 결과를 구체적으로 합의하면 ‘검색이 된다’의 의미가 서로 달라지는 일을 줄일 수 있습니다.

가상 업무 예시

고객센터에서 ‘김민수’를 검색했더니 동명이인 두 명이 나왔는데 첫 번째 고객만 표시돼 다른 사람의 주문을 안내했습니다. 팀은 ‘동명이인 두 명을 등록한 상태에서 이름을 검색하면 두 행을 표시하고, 상담 권한 안에서 고객 번호로 구별한다’를 합격 기준으로 적었습니다. 없는 이름은 ‘검색 결과 없음’을 표시하는지도 함께 확인합니다.

3. 업무 규칙 — 프로그램이 지켜야 할 약속을 찾는다

업무 규칙은 할인 조건이나 취소 기한처럼 프로그램이 지켜야 할 기준입니다. 같은 규칙을 여러 화면에 따로 구현하면 하나만 고쳤을 때 결과가 달라질 수 있습니다.

모듈은 맡은 역할에 따라 나눈 프로그램 부분입니다. 할인 계산을 담당할 공통 모듈을 두고 각 화면이 그 결과를 사용하게 하면 규칙을 한곳에서 관리할 수 있습니다. 사용자가 화면을 거치지 않고 요청할 수도 있으므로 중요한 규칙은 실제 처리를 맡은 서버에서도 확인해야 합니다.

가상 업무 예시

주문 취소 기한을 웹 화면에만 넣으면 다른 경로로 들어온 요청에서는 기한을 넘긴 취소가 처리될 수 있습니다. 서버에서도 취소 가능 여부를 판단하고, 출고가 시작된 주문은 별도 절차로 안내하도록 만듭니다.

4. 점증적 개발 — 작은 변경으로 일찍 확인한다

점증적 개발은 핵심 기능부터 동작하게 만든 뒤 기능을 더해 가는 방식입니다. 진화적 개발은 사용하면서 발견한 변경 사항을 다음 버전에 반영하는 방식입니다. 실제 개발에서는 두 방식을 함께 사용할 수 있습니다.

배송지 입력부터 개선해 사용자가 제대로 입력하는지 확인한 뒤 다른 기능을 넓히면 잘못된 가정을 일찍 찾을 수 있습니다. 다만 입력 화면만 바꾸고 기존 주문 저장과 연결되지 않으면 쓸 수 없으므로, 작은 단위도 실제 사용 흐름이 이어지게 구성해야 합니다.

가상 업무 예시

배송지 화면 전체를 개편하기 전에 우편번호 검색과 주소 저장까지만 한 흐름으로 만들어 일부 고객에게 제공합니다. 시험에서 도로명 주소를 모르는 고객이 입력을 끝내지 못하자 직접 입력 경로를 보완합니다. 그다음 배송 요청사항 기능을 추가합니다. 작은 버전에서도 주문을 끝낼 수 있어야 실제 불편을 일찍 발견할 수 있습니다.

5. 응집도와 결합도 — 모듈의 역할을 모으고 서로의 의존을 줄인다

모듈은 할인 계산이나 주문 저장처럼 역할에 따라 나눈 프로그램 부분입니다. 응집도는 한 모듈 안의 내용이 같은 목적에 얼마나 관련돼 있는지, 결합도는 다른 모듈에 얼마나 의존하는지를 나타냅니다.

할인 계산과 화면 색상 처리가 뒤섞이면 요금 규칙을 바꾸다가 화면 코드까지 건드리기 쉽습니다. 계산은 공통 모듈에 모으고 화면은 결과를 보여 주게 나누면 변경 범위를 이해하기 쉬워집니다. 파일 수를 늘리는 것보다 관련 역할을 모으고 불필요한 연결을 줄이는 것이 목적입니다.

가상 업무 예시

할인율이 바뀔 때 고객용 화면과 관리자 화면을 따로 수정하면 한쪽을 빠뜨릴 수 있습니다. 할인 금액은 공통 계산 함수에서 구하고, 두 화면은 그 결과를 보여 주도록 나누면 같은 규칙을 여러 번 고치는 일을 줄일 수 있습니다.

6. 검증 — 중요한 실패를 먼저 잡는다

명세 기반 테스트는 프로그램이 해야 한다고 정한 동작에서 시험할 조건을 찾는 방법입니다. 경계값 분석은 허용 범위의 끝과 그 주변을, 상태전이 시험은 현재 상태에서 어떤 사건이 생겼을 때의 변화를 확인합니다.

주문 수량이 1부터 10까지라면 1·10뿐 아니라 0·11도 확인할 수 있습니다. 결제 실패 뒤 재고가 돌아오는지, 버튼을 두 번 눌러도 중복 주문이 생기지 않는지도 중요한 시험입니다. 시험 수를 늘리는 데서 끝내지 말고 어떤 잘못된 결과와 피해를 막는지 확인합니다.

가상 업무 예시

한정 상품은 한 사람당 최대 10개만 살 수 있습니다. 정상 주문 2개만 시험하면 11개 구매도 허용하는 오류를 놓칩니다. 담당자는 0·1·10·11개를 주문해 경계를 확인하고, 결제 거절 시 확보했던 재고가 반환되는지도 검사합니다. 판매 제한 위반과 팔리지 않은 재고의 장기 점유를 각각 막는 시험입니다.

7. 트랜잭션과 실패 처리 — 응답이 끊겨도 실제 처리 결과를 확인한다

트랜잭션은 함께 성공하거나 모두 취소돼야 하는 데이터 작업의 단위입니다. 하지만 내 프로그램의 트랜잭션이 외부 결제 업체의 처리까지 자동으로 되돌리는 것은 아닙니다.

결제를 요청한 뒤 응답을 받지 못해도 업체에서는 이미 결제가 끝났을 수 있습니다. 바로 새 결제를 요청하면 두 번 청구될 수 있으므로 같은 요청을 구분할 번호와 실제 상태 확인이 필요합니다. 이미 처리된 요청에는 기존 결과를 돌려주는 등의 방식으로 중복 처리를 막아야 합니다.

가상 업무 예시

결제 요청 뒤 통신이 끊겼다고 다시 결제하면 두 번 청구될 수 있습니다. 요청을 식별할 번호를 사용하고 결제 상태를 먼저 조회해, 이미 처리된 요청은 그 결과를 돌려주도록 합니다.

8. 리팩토링 — 기존 동작을 보존하며 개선한다

리팩토링은 사용자가 보는 동작을 유지하면서 프로그램 내부 구조를 개선하는 작업입니다. 기능 추가나 동작 변경과 목적이 다르므로 기존에 지켜야 할 동작부터 확인해야 합니다.

오래된 날짜 보정 코드가 지저분해 보여도 해외 지점의 마감 시간을 처리할 수 있습니다. 그 조건을 재현하는 시험을 먼저 마련하고 구조를 정리합니다. 수정 후 기존 동작이 망가지지 않았는지 확인하는 회귀 시험으로 필요한 예외가 사라지지 않게 합니다.

가상 업무 예시

9. 배포와 복구 — 실제 환경에서 확인하고 실패 시 되돌린다

14. FSM과 상태 전이 — 현재 상태에서 가능한 다음 동작을 정한다

15. 인터페이스 계약 — 프로그램 사이의 입력·출력 규칙을 관리한다

인터페이스 계약은 프로그램끼리 어떤 입력을 보내고 어떤 형식의 결과와 오류를 돌려줄지 정한 약속입니다. 받는 쪽은 그 약속을 기준으로 값을 읽고 다음 일을 합니다.

가격을 숫자로 보내다가 예고 없이 ‘10,000원’이라는 문자열로 바꾸면 앱의 계산이 실패할 수 있습니다. 새 형식이 필요하면 새 항목을 추가하고 기존 방식의 지원 기간과 전환 날짜를 알립니다. 이용하는 프로그램이 바뀌었는지 확인한 뒤 옛 형식을 정리합니다.

가상 업무 예시

가격 응답을 숫자에서 통화 포함 문자열로 바로 바꾸면 앱 계산이 실패할 수 있습니다. 새 필드를 추가하고 기존 소비자가 전환했는지 확인한 후 옛 필드를 정리합니다.

16. 의존성 관리 — 외부 코드를 제품의 일부로 취급한다

의존성은 프로그램이 실행되기 위해 사용하는 외부 코드나 도구와의 관계입니다. 라이브러리는 자주 쓰는 기능을 모아 재사용하게 만든 코드입니다. 가져다 쓰면 개발 시간을 줄일 수 있지만 그 버전과 변경도 제품의 일부로 관리해야 합니다.

날짜 표시 라이브러리를 업데이트했을 때 시간 계산 방식이 달라질 수 있습니다. 사용한 버전을 기록해 같은 조건으로 다시 만들 수 있게 하고, 업데이트 후 중요한 날짜 계산과 프로그램 크기 등을 확인합니다. 필요하지 않은 기능까지 가져오는 것은 아닌지도 검토합니다.

가상 업무 예시

예약 날짜를 계산하는 외부 라이브러리의 버전을 고정하지 않아, 같은 소스로 다시 배포했는데 다음 달 예약일 계산이 달라졌습니다. 팀은 사용 버전을 기록하고 업데이트를 별도 변경으로 관리합니다. 월말·윤년 날짜를 확인한 뒤 새 버전을 적용하고, 실패하면 확인된 이전 버전으로 다시 빌드합니다.

17. 설정 분리 — 시험 서버와 실제 서비스의 설정을 구분한다

설정은 접속할 서버 주소나 실행 모드처럼 프로그램의 동작 조건을 정하는 값입니다. 시험 환경과 실제 서비스가 같은 코드를 써도 설정은 달라야 할 수 있습니다.

시험 서버의 기본 결제 주소가 실제 결제 업체를 향하면 시험 주문이 실제 청구로 이어질 수 있습니다. 환경별 설정을 구분하고 필수 값이 없으면 조용히 실제 주소를 쓰지 않도록 합니다. 소스 변경을 빌드·시험으로 이어 주는 지속적 통합(CI) 과정에서도 적용할 설정과 대상을 확인합니다.

가상 업무 예시

18. 사용자 경험 — 오류가 나도 작업을 이어 갈 수 있게 돕는다

사용자 경험에는 정상 처리뿐 아니라 오류가 났을 때 작업을 회복하는 과정도 포함됩니다. 무엇을 고쳐야 하는지 모르면 사용자는 같은 실패를 반복하거나 처음부터 다시 작성해야 합니다.

긴 신청서를 보냈는데 첨부 파일 형식이 틀렸다면 이미 입력한 내용을 유지하고 수정할 파일과 허용 형식을 알려 줍니다. 내부 오류 코드를 그대로 표시하는 것보다 사용자가 다음 행동을 결정할 수 있는 정보를 제공해야 합니다.

가상 업무 예시

19. 기술 부채 — 개선을 미룰 때 늘어날 유지보수 비용을 기록한다

기술 부채는 중복 코드나 임시 처리 때문에 나중의 변경과 오류 수정에 더 많은 비용이 드는 상황을 설명하는 말입니다. 오래된 코드라는 이유만으로 모두 기술 부채라고 판단하지는 않습니다.

임시로 여러 곳에 복사한 할인 코드를 매번 함께 고쳐야 한다면 반복 수정 시간과 누락 오류를 기록합니다. 개선에 드는 비용과 앞으로 줄일 부담을 비교하고, 당장 미룬다면 위험과 다시 검토할 시점을 남깁니다.

가상 업무 예시

급한 행사 때문에 할인 조건을 웹·앱·관리자 코드에 복사했습니다. 이후 할인율을 바꿀 때마다 세 곳을 수정해야 했고, 한 곳을 빠뜨려 고객마다 다른 금액이 나왔습니다. 팀은 공통 계산으로 정리하는 데 이틀이 필요하다고 기록하고 다음 할인 행사 전에 개선하기로 했습니다. 임시로 아낀 시간이 이후의 반복 수정과 오류 비용으로 돌아온 상황입니다.

20. 문제 재현 — 추측보다 증거로 원인을 좁힌다

문제 재현은 오류가 난 입력과 환경, 순서를 맞춰 같은 실패를 다시 확인하는 것입니다. 기대 결과와 실제 결과의 차이를 기록하면 무엇을 고쳐야 하는지와 수정이 효과가 있는지 비교할 수 있습니다.

특정 고객의 총액만 다르다면 할인 중복·반올림·통화 설정을 비교합니다. 실패를 만드는 최소 조건을 찾고 수정한 뒤 같은 입력으로 다시 시험합니다. 오류 메시지가 안 보인다는 이유만으로 정상 결과가 나왔다고 판단하지 말고 계산과 저장 결과도 확인합니다.

가상 업무 예시

1만 원 상품에 10% 쿠폰을 적용하면 9천 원이어야 하는데, 같은 쿠폰을 다시 선택하면 8,100원이 됐습니다. 개발자는 ‘상품 선택 → 쿠폰 적용 → 같은 쿠폰 재선택’ 순서로 오류를 재현했습니다. 수정 후 같은 순서에서도 9천 원인지, 쿠폰을 해제하면 1만 원으로 돌아오는지 확인합니다.
