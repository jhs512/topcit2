소프트웨어 개발

코드를 작성하는 속도보다, 필요한 동작을 정확히 만들고 안전하게 바꿀 수 있는지가 중요합니다.

교재 개념을 먼저 설명하고 실무 판단과 가상 예시로 연결한 자체 해설입니다. 각 항목의 관련 교재 내용에서 단원과 PDF 페이지를 확인할 수 있습니다. 20개 노트는 교재 전체 요약이나 시험 중요도 순위가 아니며, 주제 끝의 추가 학습 내용도 함께 확인하세요.

핵심 개념 20가지

  1. 요구사항 추출 — 만들기 전에 불편을 확인한다
  2. 테스트 케이스와 완료 기준 — 같은 결과를 확인한다
  3. 업무 규칙 — 프로그램이 지켜야 할 약속을 찾는다
  4. 점증적 개발 — 작은 변경으로 일찍 확인한다
  5. 응집도와 결합도 — 역할과 변경 영향을 나눈다
  6. 검증 — 중요한 실패를 먼저 잡는다
  7. 트랜잭션과 실패 처리 — 중간에 끊긴 결과를 확인한다
  8. 리팩토링 — 기존 동작을 보존하며 개선한다
  9. 배포와 복구 — 사용자에게 전달할 때까지 책임진다
  10. 관찰과 피드백 — 공개 후 실제 사용을 확인한다
  11. 형상관리와 버전 기록 — 변경의 이유를 남긴다
  12. 코드 검토 — 다른 사람이 이해할 수 있는지 확인한다
  13. 동시성 — 여러 사용자가 함께 행동하는 상황을 다룬다
  14. FSM과 상태 전이 — 가능한 다음 행동을 제한한다
  15. 인터페이스 계약 — 연결 상대와 약속을 관리한다
  16. 의존성 관리 — 외부 코드를 제품의 일부로 취급한다
  17. 설정 분리 — 환경 차이를 명시한다
  18. 사용자 경험 — 성공뿐 아니라 회복을 돕는다
  19. 기술 부채 — 나중에 갚을 비용을 드러낸다
  20. 문제 재현 — 추측보다 증거로 원인을 좁힌다

1. 요구사항 추출 — 만들기 전에 불편을 확인한다

요구사항 공학은 이해관계자의 필요를 추출·분석·명세·검증하고 변경을 관리하는 활동입니다. 요구 추출에서는 사용자가 제시한 기능과 그 기능으로 해결하려는 업무 문제를 함께 확인합니다. 사용자가 요청한 기능은 해결책에 대한 제안일 수 있으므로, 그 기능이 필요한 상황과 현재 겪는 어려움을 먼저 확인해야 합니다. 잘못 짚은 문제를 빠르게 구현해도 업무는 나아지지 않습니다.

가상 업무 예시

직원이 엑셀 내려받기 버튼을 요청했다고 합시다. 이유를 물어보니 주문 누락을 찾으려고 매일 두 목록을 비교하고 있었습니다. 파일 제공뿐 아니라 누락 주문을 바로 보여 주는 방법도 함께 검토할 수 있습니다.

현장에서 확인할 질문
누가 어떤 상황에서 무엇을 못 하고 있으며, 이번 변경으로 그 일이 어떻게 쉬워집니까?

2. 테스트 케이스와 완료 기준 — 같은 결과를 확인한다

테스트 케이스는 사전 조건, 입력, 수행 절차, 기대 결과를 명시한 검증 단위입니다. 완료 기준을 이 형식으로 정하면 개발자와 사용자가 같은 결과로 합격 여부를 판단할 수 있습니다. 어떤 입력을 받고 어떤 결과를 내야 하는지, 결과가 없거나 입력이 잘못되면 어떻게 처리할지 구체적인 예로 합의해야 합니다. 이 예들은 나중에 결과를 확인하는 기준이 됩니다.

가상 업무 예시

고객 검색에서 이름이 같은 사람이 두 명 나올 수 있습니다. 이름만 보여 줄지, 식별에 필요한 추가 정보를 권한에 맞게 보여 줄지 정하고, 검색 결과가 없을 때의 안내도 함께 확인합니다.

현장에서 확인할 질문

3. 업무 규칙 — 프로그램이 지켜야 할 약속을 찾는다

모듈화는 시스템을 역할별 구성요소로 나누는 설계 원리입니다. 같은 업무 규칙을 여러 모듈에서 다르게 구현하면 변경의 일관성이 깨지므로 그 규칙을 책임질 곳을 정해야 합니다. 규칙을 화면마다 따로 구현하면 같은 요청이 들어와도 처리 경로에 따라 다른 결과가 나올 수 있습니다. 같은 의미의 규칙을 어디에서 책임질지 정하고 예외를 함께 기록해야 합니다.

가상 업무 예시

주문 취소 기한을 웹 화면에만 넣으면 다른 경로로 들어온 요청에서는 기한을 넘긴 취소가 처리될 수 있습니다. 서버에서도 취소 가능 여부를 판단하고, 출고가 시작된 주문은 별도 절차로 안내하도록 만듭니다.

4. 점증적 개발 — 작은 변경으로 일찍 확인한다

점증적 개발은 핵심 기능부터 동작하게 만들고 기능을 확장하는 방식이며, 진화적 개발은 사용 중 발견한 변경을 다음 버전에 반영하는 방식입니다. 작은 변경과 빠른 피드백은 이 원리를 적용하는 방법입니다. 사용자가 실제로 확인할 수 있는 작은 단위로 나누면 잘못된 가정도 일찍 발견할 수 있습니다. 단, 서로 맞물려야 하는 데이터와 기능을 무리하게 분리해서는 안 됩니다.

가상 업무 예시

주문 화면 전체를 바꾸기 전에 배송지 입력 개선부터 적용합니다. 일부 사용자에게 먼저 보여 주고 입력 실패와 문의를 확인한 뒤 범위를 넓힙니다. 기존 주문 흐름과 호환되는지도 함께 확인합니다.

5. 응집도와 결합도 — 역할과 변경 영향을 나눈다

응집도는 모듈 내부 요소가 공통 목적과 관련된 정도이고, 결합도는 다른 모듈에 의존하는 정도입니다. 기능적 독립성을 높여 변경 영향을 좁히는 것이 설계의 목표입니다. 화면 표현, 업무 판단, 데이터 저장처럼 바뀌는 이유가 다른 책임을 구분하면 변경의 영향을 이해하기 쉽습니다. 파일을 많이 만드는 것 자체가 좋은 구조는 아닙니다.

가상 업무 예시

할인 정책이 바뀔 때 웹 화면과 관리자 화면을 각각 수정해야 한다면 규칙이 흩어져 있는지 살펴봅니다. 공통 할인 판단을 한곳에서 책임지게 하고, 각 화면은 판단 결과를 사용자에게 보여 주도록 나눕니다.

6. 검증 — 중요한 실패를 먼저 잡는다

명세 기반 테스트는 요구된 동작에서 시험을 도출합니다. 경계값 분석은 입력 범위의 경계를, 상태전이 시험은 현재 상태와 사건에 따른 변화를 확인합니다. 위험이 큰 계산, 권한, 상태 변경과 이미 발생했던 오류를 우선해서 검사합니다. 테스트 개수보다 어떤 피해를 막는지가 중요합니다.

가상 업무 예시

주문 시스템이라면 정상 결제뿐 아니라 결제 실패 때 재고가 원상복구되는지, 버튼을 두 번 눌러도 중복 주문이 생기지 않는지를 확인합니다. 실제 서비스에서 사용되는 연결 과정도 함께 검사합니다.

7. 트랜잭션과 실패 처리 — 중간에 끊긴 결과를 확인한다

트랜잭션은 함께 성공하거나 취소해야 할 데이터 작업 단위입니다. 다만 외부 결제까지 걸친 통신에서 응답을 받지 못했다는 사실은 거래가 취소되었다는 증거가 아니므로 결과 확인과 중복 방지를 별도로 설계해야 합니다. 실패했다는 응답이 없어도 실제 처리가 끝났을 수 있으므로, 무조건 재시도하면 중복 처리가 생깁니다. 처리 상태를 식별하고 재시도해도 같은 업무가 반복되지 않도록 설계해야 합니다.

가상 업무 예시

결제 요청 뒤 통신이 끊겼다고 다시 결제하면 두 번 청구될 수 있습니다. 요청을 식별할 번호를 사용하고 결제 상태를 먼저 조회해, 이미 처리된 요청은 그 결과를 돌려주도록 합니다.

8. 리팩토링 — 기존 동작을 보존하며 개선한다

리팩토링은 외부에서 보이는 동작을 유지하면서 내부 구조를 개선하는 작업입니다. 기존 예외의 의미를 확인하고 회귀 시험을 마련해야 구조 개선 중 필요한 동작이 사라지는 일을 막을 수 있습니다. 삭제하거나 다시 만들기 전에 사용 경로와 필요한 동작을 확인해야 합니다. 재작성 여부는 외형보다 위험과 유지 비용을 비교해 판단합니다.

가상 업무 예시

오래된 날짜 보정 코드를 지우려다가 해외 지점의 마감 시각을 처리하는 코드임을 알게 됐다고 합시다. 먼저 해당 동작을 재현해 보호하고, 지점별 시간 처리 규칙을 드러내는 방향으로 정리합니다.

9. 배포와 복구 — 사용자에게 전달할 때까지 책임진다

1. 스택과 큐

스택은 마지막에 넣은 원소를 먼저 꺼내는 LIFO, 큐는 먼저 넣은 원소를 먼저 꺼내는 FIFO 구조입니다. 재귀 호출 관리와 대기 작업 처리처럼 꺼내는 순서가 다른 문제에 알맞은 구조를 선택합니다.

2. 이진 탐색과 깊이 우선 탐색

이진 탐색은 정렬된 자료의 중간값과 비교해 탐색 범위를 절반씩 줄입니다. 깊이 우선 탐색은 한 경로를 먼저 깊이 따라간 뒤 되돌아오며, 스택이나 재귀 호출로 구현할 수 있습니다.

3. UML과 디자인 패턴

UML은 구조와 동작을 여러 관점의 다이어그램으로 표현하는 모델링 언어입니다. 디자인 패턴은 반복되는 설계 문제에 활용할 수 있는 해결 구조를 정리한 것으로, 완성된 코드 자체와는 다릅니다.

4. 컴파일러와 인터프리터
